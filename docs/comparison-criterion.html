tpt-benchmark vs Criterion: identical workloads

This note records a head-to-head run of tpt-benchmark and Criterion 0.5.1 on the same four workloads, on the same machine, back to back. It answers two questions from todo.md:

  1. Do the two 95% confidence intervals of the mean agree for each workload?
  2. How long does each framework take to finish each workload?

Method

  • Workloads live in crates/tpt-benchmark/benches/common/workloads.rs and are included by both benches with #[path], so the measured code is the same source file.
  • Criterion side: crates/tpt-benchmark/benches/vs_criterion.rs, Criterion 0.5.1 with default-features = false (no plots, no rayon). Interval read from target/criterion/<name>/new/estimates.json, mean.confidence_interval.
  • tpt side: crates/tpt-benchmark/benches/vs_tpt.rs, WallClock layer only, default Config. Interval read from target/tpt-benchmark/tpt-benchmark.json, ci_low / ci_high, plus stop_reason.
  • Driver: scripts/compare.ps1. It builds both benches first with --no-run (compile time excluded), then runs vs_criterion and vs_tpt back to back for 3 rounds. Each cargo bench invocation is wall-timed with Measure-Command. Medians of the CI bounds and the spread across rounds are computed from the output files.
  • Reference timer (sanity check, not a framework): the same workloads.rs compiled standalone with rustc -O and timed with a plain std::time::Instant loop (best of five). It is only used to judge which framework's numbers look right; it is not a statistical method.
  • Environment: Windows 11, Intel i7-12700 (8 P-cores + 4 E-cores, hybrid), release/bench profile. The machine was shared with other agents' cargo and miri processes during the run, so the numbers carry some load noise. Compile times on Windows are much slower than Linux; they are excluded here.
  • Source revision: the timed runs used a snapshot of commit d6280c1 (git archive HEAD) with this work's Cargo.toml and bench files overlaid. The live working tree had another agent's in-progress edits to src/bencher.rs that did not compile at the time, so the numbers were not taken from it. The snapshot's library is therefore the committed one.

Investigation (re-run, quiet machine)

The loaded-machine run above disagreed with the reference on every workload. The investigation tested whether that was a bug in either framework.

  • Same code, same binary, three timers. A scratch binary timed the sum with a raw loop, with tpt_benchmark::measure, and with Criterion in one process. Raw: 70 ns. tpt: 69 ns. Criterion: 168 ns. Changing Criterion's closure body (inlining the sum) or its black_box (standard instead of volatile) did not change its result, so the code and the harness's black_box are not the cause.
  • Order and time in the process. With Criterion run first, it measured 68 to 72 ns, the same as the raw loop. Criterion's per-sample times in the slow run were flat across sample sizes (about 157 to 188 ns), so this is not a regression-slope artefact.
  • Separate processes. Six standalone Criterion processes measured 68 to 72 ns. The slow reading did not recur.
  • Under contention. With all 20 logical cores busy, Criterion measured 87 to 89 ns and tpt 67 to 71 ns. The slow reading did not recur.
  • The real comparison benches, quiet machine. Run as the comparison itself, one full pass of each:

Changes made: outlier threshold 3 → 5 scaled MADs, SPRT p0 0.01 → 0.02 and p1 0.10 → 0.20, and burn-in draws excluded from the SPRT. What this shows:

  • The gate now behaves as designed. Quiet rounds converge with the noisy flag clear. Rounds with 2 to 10 % outliers are flagged noisy and run to the cap, which is an honest report of an unstable environment.
  • Outlier rates vary between rounds, so runs at the same workload are not equal. Precise runs still cap when the environment is noisy.
  • Tpt and Criterion intervals now overlap on some rounds and not others. The gap is 1 to 5 %, not the earlier 2x. Format disagrees in all three tpt rounds, and dot in two. The fast multiply is at the timer floor.
  • Wall time is still not a like-for-like comparison, because the two tools do not target the same interval.

Conclusions

  1. The earlier "CIs do not agree" conclusion is withdrawn. It was measured on a loaded machine and did not reproduce on a quiet one. On the quiet run, the sum and format intervals overlap. The dot product intervals do not overlap, with tpt 2.6% higher. The fast multiply is at the timer floor and is not meaningful.

  2. Remaining issue in tpt: the noise gate stops convergence for precise runs. The sum and fast multiply hit the 1000-draw cap, with relative intervals of 0.24% and 0.19% (far inside the 2% target). About 10% of their draws were flagged as outliers, which sits right at the SPRT's noisy rate p1 = 0.10. The test then returns no decision, so the run continues to the cap, and the result is marked noisy. This is a tuning question in the engine, not a measurement error. It makes runs slower and marks precise results as noisy.

  3. Wall time. On the loaded run tpt took about 1.8 s per bench against about 47 s for Criterion, roughly 25 times less. That mostly reflects Criterion's default budgets (5 s measurement, 3 s warm-up), not equal precision. On the quiet run the sum and format benches stopped after 907 and 31 draws respectively. A fair time-to-precision comparison needs both tools set to the same target interval.

  4. "Faster than Criterion" is not measured here. The accuracy question is settled: the two agree on the sum and format workloads. A speed claim needs time-to-equal-precision, which this run does not provide.

Divan

Divan is deferred, not added. Adding it would need another dev-dependency, another bench target and another full run for a three-way comparison, and the two-way result above already fails the agreement test. A Divan comparison is worth doing only after the Criterion interval disagreement is explained. This document is the only place that records the deferral; todo.md was not edited.

Reproducing

pwsh -File scripts/compare.ps1 -TargetDir <absolute path to a private target dir> -Runs 3

Output: a table on stdout and <TargetDir>/compare-results.json with every round's CI, mean, stop reason and wall time. The Criterion JSON lands in <TargetDir>/criterion/, not target/criterion/, because CARGO_TARGET_DIR is set for these runs.

Limitations

  • Single machine, Windows, hybrid CPU, shared with other agents' builds. No pinning or isolation was applied.
  • Three rounds of the driver plus two diagnostic rounds. The spread across rounds is small relative to the Criterion/tpt gap, but this is not a statistical test of the gap.
  • The reference timer is a single-loop Instant measurement, used only as a sanity check.
  • Criterion was run at 0.5.1. Criterion 0.7.0 is available but was not tested.
  • Linux was not measured.
Built with tpt-benchmark. Hosted CI runners are noisy and usually have no hardware counters, so compare trends on one machine rather than absolute numbers.
