Migrating from Criterion

This guide maps a Criterion benchmark suite onto tpt-benchmark. It covers the code changes, the command-line flags, the output locations and what has no equivalent yet. Features that are not implemented are listed at the end, so check that section before you start.

The Criterion-side names below follow Criterion's documented API as we know it. They were not re-checked against a Criterion release for this guide. The tpt-benchmark side was checked against the source.

Cargo.toml

Keep harness = false. Remove the criterion dev-dependency and add tpt-benchmark:

[dev-dependencies]
tpt-benchmark = "0.1"        # not yet on crates.io; use a path or git dependency until it is published

[[bench]]
name = "sums"
harness = false

A single benchmark

Criterion:

use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn sum(c: &mut Criterion) {
    c.bench_function("sum", |b| b.iter(|| black_box(1 + 1)));
}

criterion_group!(benches, sum);
criterion_main!(benches);

tpt-benchmark:

use tpt_benchmark::{Bencher, black_box, tpt_bench, tpt_bench_group};

#[tpt_bench_group]
mod arith {
    use super::*;

    #[tpt_bench]
    fn sum(b: &mut Bencher) {
        b.iter(|| black_box(1 + 1));
    }
}

tpt_benchmark::main!(arith);

Points to note:

  • criterion_group! and criterion_main! are replaced by tpt_bench_group on a module and tpt_benchmark::main!. Each main! argument is a group module.
  • The benchmark function takes b: &mut Bencher and must call one of the measuring methods (b.iter, b.iter_batched, b.iter_async) exactly once. It must return ().
  • The benchmark's name is group::function, so sum in mod arith is arith::sum. Filters and baselines use that name.
  • black_box is re-exported from std::hint::black_box. Import it from tpt_benchmark, not from criterion.

Parameterised benchmarks

Criterion's BenchmarkId and bench_with_input become args = [...]. Each value produces one benchmark. Its name is the function name, a slash, and the text of the expression:

#[tpt_bench(args = [128, 1024])]
fn sum(b: &mut Bencher, n: usize) {
    let data: Vec<u64> = (0..n as u64).collect();
    b.iter(|| black_box(&data).iter().sum::<u64>());
}

This is benchmarked as arith::sum/128 and arith::sum/1024. Build the input once, outside iter, as shown.

Layers

Criterion measures wall time only. In tpt-benchmark, wall time is the default layer and needs no attribute. The other layers are selected with #[layers(...)] on a group or on one benchmark:

#[tpt_bench_group]
#[layers(WallClock, Allocations)]
mod parse { /* ... */ }

Valid names are WallClock, Allocations, AllocBytes, HardwareCounters, HwInstructions, HwL1Misses, HwL2Misses and HwBranchMisses. The allocation layers need #[global_allocator] (see allocations.md). Hardware counters work on Linux only (see layers.md).

Command-line flags

Run the bench as before with cargo bench. Arguments after -- go to the binary.

tpt-benchmark exits with code 1 when a significant regression exceeds the threshold, which makes it usable as a CI gate.

Options not listed above are an error (exit code 2), for example --sample-size, --measurement-time, --warm-up-time, --load-baseline and --significance-level. Remove them from scripts.

The JSON file is versioned (schema_version) and is described in json-schema.md. Its contents differ from Criterion's estimates.json, so update any scripts that read it.

Baseline names may contain letters, digits, -, _ and .. Any other character is rejected. Baselines saved by Criterion cannot be read by tpt-benchmark, and the reverse is also true. Re-save the baselines you need with the new tool.

Configuration

Criterion lets you set sample size, measurement time and warm-up time per group. tpt-benchmark does not have per-benchmark configuration. The Config (warm-up, minimum batch, engine settings) is used for every benchmark, and the --quick flag is the only tuning switch on the command line. Set your own Config by calling tpt_benchmark::measure directly if you need other values.

What is not supported

These are checked against crates/tpt-benchmark/src/bencher.rs and the macros crate. They have not been implemented.

  • iter_batched_ref, iter_with_setup and the BatchSize argument. Use Bencher::iter_batched(setup, routine), which exists. Its setup runs outside the timed region, and each batch is capped at 1024 iterations because the inputs for a batch are built together. The Criterion names and the BatchSize enum have no counterpart.
  • Async async fn benchmark functions. The #[tpt_bench] macro rejects them with "async benchmark functions are not supported". Write a normal function and call Bencher::iter_async(|| async { ... }), or Bencher::iter_async_with(executor, ...) to use your runtime's block_on.
  • Confidence levels other than 0.95. The engine computes a 95 % interval only.
  • Regex filters. The filter is a substring match, or an exact match with --exact.
  • Separate report pages. The HTML report is one index.html with a section per benchmark and inline SVG charts. There are no per-group or per-benchmark pages.
  • Per-benchmark configuration through attributes (see above).
  • Criterion-compatible files. No shim. criterion:: imports cannot be replaced by a re-export.

If your suite uses one of these, plan to keep it on Criterion until it is supported.

Built with tpt-benchmark. Hosted CI runners are noisy and usually have no hardware counters, so compare trends on one machine rather than absolute numbers.
